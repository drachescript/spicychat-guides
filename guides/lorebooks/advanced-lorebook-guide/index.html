Advanced Lorebook Guide For Authors

A condensed version of Sydd's thread about getting Lorebook entries to trigger more reliably without flooding context.

The big thing to remember: Lorebook keywords trigger from words that actually appear in the conversation. Putting a keyword in the persona, scenario or another Lorebook entry does not directly trigger it.

The trigger rule

The guide's most important point is the difference between triggering and anchoring. A keyword has to appear in chat — either in the user's message or the model's reply — before the matching Lorebook entry can activate.

You can still put a specific term in the character/persona to encourage the model to naturally use that term later. That is anchoring. It makes a trigger more likely to appear in chat, but it is not a trigger by itself.

Keep entries small

The thread recommends splitting large blocks into smaller entries and generally aiming for entries under roughly 100 tokens where possible. The point is not the exact number; it is to avoid spending a large chunk of context every time one keyword fires.

  • Small entries are easier to trigger precisely.
  • Several relevant entries can stack without dumping a huge block at once.
  • Detailed information stays conditional instead of sitting in context all the time.

Think of the Lorebook as a reference library, not one giant encyclopedia page.

Use wildcards carefully

A wildcard is an asterisk attached directly to the keyword. A suffix wildcard is usually the useful one:

lunara*

That can catch forms such as lunara, lunara's or lunaras. It does not cross spaces. Prefix wildcards such as *book are valid but much easier to trigger accidentally.

Avoid *word*. The original guide warns that wildcards on both sides become far too greedy and can cause constant unwanted triggers.

Umbrella entries vs. specific entries

Broad keywords are risky because they can fire constantly. A better pattern is a short umbrella entry that introduces the system, then separate detailed entries for the parts of that system.

Umbrella:
adventurer*
adventurer guild*

Only explains that the guild exists and has ranks.

Specific:
mithril-rank*
mithril rank*

Explains what Mithril rank actually means.

The broader the keyword, the shorter and more factual the entry should be. Save mechanics, consequences and detailed behavior for the specific entries.

Anchor terms the model should naturally say

If a concept matters to a character, give it a distinctive name and use that name in the character information. The thread uses Mark of the Deep as an example: instead of a generic keyword such as curse, the Lorebook can use mark of the deep*, while the character description makes the mark important enough that the model is likely to mention it.

Anchoring is iterative. If the model keeps saying mithril-ranked while your keyword is only mithril rank, add a keyword that matches the phrasing the model actually uses.

Layer information

Umbrella entries, anchored terms and specific entries work best together. The umbrella gives the model the vocabulary and overall structure; the specific entry only appears when the conversation reaches that part.

This is especially useful for shared world Lorebooks used by multiple bots. Avoid generic triggers such as {{user}} or {{char}} for world information that is not relevant to everyone.

Test the bot, then adjust the keywords

  • Watch the exact words the model naturally uses.
  • Add useful variations instead of piling on generic keywords.
  • Try to avoid triggering a large number of entries in the same message.
  • Keep the text factual and compact instead of writing it like prose.
  • For character entries, keep the always-needed identity brief: traits, role, goals and a short description.
  • Use clear entry names for your own organization; the entry title itself is not a keyword.
