What this guide is

The thread was explicitly created as a community guide rather than an official SpicyChat document. Its original index covered formatting, Personas, example dialogue, prompt snippets, AI art, SFW/slow-burn prompting, multiple-character bots, greetings, personality, tagging, generation settings and other creator tools.

That matters because some parts are timeless writing advice while others describe how SpicyChat or its models worked in 2024. This page keeps the useful detail but labels the older implementation-specific bits instead of pretending every old number or model behavior is still current.

Formatting styles for character information

The first large section explains formatting as a way to make the character information easier for the model to interpret consistently. The thread gives three main approaches plus PList-style examples.

Boost / trait-list style

Jack Sparrow + Pirate + Charismatic + 35 years old + black hair

This is compact and easy to scan, but it can lose nuance when everything gets reduced to single words.

W++ / field style

Name: Jack Sparrow
Age: 35
Occupation: Pirate
Personality: Charismatic
...

Fields separate different kinds of information and make it obvious what each detail is supposed to describe.

Natural language

Captain Jack Sparrow is a 35-year-old charismatic pirate
who sails the seas looking for treasure and adventure.

Natural language can carry more voice and context, especially when a trait needs explanation instead of a label.

PList-style writing

The thread also mentions PLists/trait lists, including modified conversational examples. The bigger lesson is not that one syntax wins. It is to choose a structure that gives the model clear, non-conflicting information.

Write with flavor, and choose words carefully

One of the strongest pieces of advice in the old guide is to make the definition sound like the character you want. If you describe a foul-mouthed, excitable character in clinical encyclopedia prose and then add ten instructions saying "do not sound like Shakespeare," you are fighting the examples you gave the model.

Flat:
likes anime

More characterful:
a total weeb who watches anime all day

The thread argues that LLMs imitate the style and associations in the text they are given, so the wording of the definition itself can do part of the work.

It also warns that some words carry strong learned associations. Its example is dominant, which can pull a character toward sexual/dominatrix behavior even if you only meant socially assertive. A word such as assertive may communicate the intended trait with less baggage. The exact model behavior changes over time, but the underlying advice still holds: think about what your chosen words usually imply in fiction and internet writing.

Personas

The thread includes an early Persona guide because the user's Persona changes what the bot knows about the person it is talking to. It distinguishes a Persona from the bot's character profile: one describes {{user}}; the other describes the character the bot is portraying.

It shows several ways to write the same Persona:

  • a normal paragraph;
  • a compact semicolon-separated trait list;
  • first-person prose;
  • third-person prose;
  • structured fields.

The 2024 post also shows JSON as an example used elsewhere and explicitly notes that JSON was not supported by SpicyChat at the time, so the useful takeaway is the structure, not that you should paste JSON into current Personas.

Example dialogue

Example dialogue tells the model what the character actually sounds like. It can demonstrate vocabulary, attitude, pacing, actions, formatting, opinions or specific knowledge that a short trait list cannot show.

The guide calls examples optional but recommended, especially when staying in-character matters. It uses <START> to separate examples:

<START>
{{user}}: Tell me about yourself.
{{char}}: ...an example written in the exact voice and style you want...

You can include both user and character turns, or just show a character response. The important part is that the sample should look like a good real response, because the model can imitate its structure.

Do not use an example merely to restate the character sheet. Use it to demonstrate things that are easier to show than describe: voice, humor, swearing level, action formatting, rhythm, emotional intensity and how the character reacts under pressure.

JED: Just Enough Description

The OP later adds a "JED" approach: give the model enough structured information to understand the character without turning every field into a biography.

Character: Raishoita Kohaku
Alias: Alyina
Age: Unknown (likely 9000+)
Gender: Female
Pronouns: She/her
Race: Anthro cat girl
Appearance: Long red hair, purple eyes, athletic body
Personality: Mischievous, curious, caring, serious

This kind of compact structure can reduce basic mistakes such as misgendering while still leaving room for actual roleplay. The thread also shows that a personality field can be longer when a character has an important duality or relationship-dependent behavior. "Just enough" does not mean "always tiny"; it means every sentence is doing useful work.

Prompt snippets: useful, but do not build the whole bot out of patches

The thread collected lots of copyable prompt snippets: not speaking for {{user}}, relationship states, language behavior, slow-burn trackers and more. It also repeatedly warns that model prompting is hit-or-miss and that piling on long corrective blocks can become token bloat.

A stable example is user-control wording:

{{char}} portrays their own actions and dialogue.
{{user}} controls their own actions, choices and dialogue.

For language behavior, the old guide suggests explicitly stating which language the character prefers and, if desired, asking for an English translation in parentheses. For relationship or slow-burn behavior, it experiments with numerical Trust/Love trackers. The thread itself notes that those trackers work on some models and not others and that they are very long for what they accomplish.

The later discussion reinforces the same point: use the smallest prompt that fixes the actual problem. More rules do not automatically mean better compliance.

Multiple-character bots

The guide's two big rules for multi-character bots are to separate each character clearly and to refer to them by their actual names rather than stuffing every person into {{char}}.

[Name: Crimson
Personality: angry, selfish, assertive
Features: floating orb, sunglasses
Accent: Southern
Relationship: rivals with Azure]

[Name: Azure
Personality: quiet, shy
Features: floating cube, fedora
Relationship: secretly in love with Crimson]

Then demonstrate both characters in the example dialogue so the model sees that each one speaks independently:

<START>
Crimson: "..."
Azure: "..."

Later in the thread, a user reports the classic problem where one member of a multi-character bot answers everything. The useful fix is still structural: make the identities distinct, name the addressed character, show turn-taking in examples, and avoid ambiguous global instructions that collapse the cast back into one voice.

The greeting / first message

The thread calls this the bot's "bread and butter." The greeting teaches the model the opening situation, response length, prose style, formatting and how much initiative it should take.

Things the guide says to avoid

  • One-line openings such as "hello user" that give the model almost nothing to imitate.
  • "Do anything" openings with no actual situation or hook.
  • Unfixed spelling/placeholder mistakes, especially conflicting {{char}}/{{user}} references.
  • Stuffing too many unrelated scene ideas into one wall of text.
  • Writing lots of assumed actions/dialogue for {{user}}, because the model may continue copying that habit.

Things it recommends

  • Give enough scenario and world context to make the opening understandable.
  • Show the interaction between the character and user instead of only describing the world.
  • Leave the greeting open enough for the user to choose what to do next when the bot is meant to support multiple routes.
  • Use the response length and formatting you want the bot to keep using.
  • Read it back for flow instead of only checking whether every lore fact was included.

A long greeting is not automatically better. The goal is enough detail to establish a clear pattern without drowning the opening in unrelated setup.

Personality, depth & tagging

The Personality/character information is where the model gets the stable facts it needs to portray the character. The thread argues for a balance: be concise enough that you are not wasting tokens, but detailed enough to capture motivations, goals, appearance, traits and the contradictions that make the character feel like a person.

The guide also includes tagging as part of bot creation. Its point is simple: accurate tags help people find the bot and help exclusion/search features work correctly. Do not add unrelated tags just for visibility.

AI art / conversation-image notes

This section is very 2024-specific. The thread describes the image pipeline and LoRA behavior as it worked at the time. The exact implementation can change, so treat the technical numbers as historical notes, not current platform documentation.

The general image advice is still useful: start with a clear, high-quality character image and define visible attributes such as hair, eyes and gender/sex cues in the character information if image generation needs to recover them from context.

The prompt-writing section breaks an image prompt into four pieces:

  • Quality tags: a small number of useful quality terms rather than a giant wall of them.
  • Subject: who/what is in the image and their visible traits.
  • State/framing: what they are doing and the camera angle.
  • Extras: background, LoRAs or other model-specific additions.
Quality: masterpiece, best quality
Subject: 1girl, blonde hair, blue eyes, street clothes
State/framing: smiling, sitting, head tilted, from below
Extras: blurry background

The guide also recommends trying a prompt without heavy weighting first and only increasing emphasis when the model is ignoring an important detail.

Generation settings

The thread explains the basic purpose of common sampling controls:

  • Top-k: limits sampling to a fixed number of the most likely next tokens.
  • Top-p: uses a probability-mass cutoff, so the number of candidate tokens can change from step to step.
  • Temperature: reshapes the probability distribution; higher values generally increase randomness, while lower values make the output more focused.

Those concepts are still useful, but exact "best" values depend on the current model. The old guide should not be treated as a fixed preset for every model SpicyChat offers today.

What the later Q&A adds

The replies after the main guide are messy, but a few recurring lessons are worth keeping:

  • Long "upgrade" prompt blocks are often token-heavy and unreliable. Take the one or two lines that solve your problem instead of copying the whole thing.
  • Positive instructions tend to work better than endless "do not" lists.
  • If you want a specific thought/narration format, show that format in examples and reinforce it in the character information.
  • If a bot repeatedly speaks as {{user}}, fix the underlying greeting/examples too; a corrective command alone may not override a strong bad pattern already present in the card or chat.
  • Different models interpret the same character card differently, so test behavior before concluding that one field or syntax is universally broken.
